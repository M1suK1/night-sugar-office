# 方案 v194 · 存档不再裁掉历史

TASK
  存档位显示「未编成 · 读回先编成」、读回来是第 14 日——
  原因是读档校验把「日志超过 300 条」当成了坏档，整份退回新开局。
  要求：历史数据一条都不要丢。

APPROACH
  1. 复现：给正常存档塞 301 条日志，`loadState` 直接 `return createInitialState()`：
     第 42 日、已编成 → 第 14 日、未编成。槽位摘要与读档共用这条路径。
  2. 根因：日志有 139 处 `unshift`，全程没有上限；校验却拿「数量」当结构错误。
  3. 修：**数量不再参与校验，也不再裁剪**——
     · logs / samples / messages 只校验「是不是数组、字段对不对」，长度不限；
     · 读档原样保留每一条；
     · `sampleFor` 里「超过 60 天就 shift」的旧限制一并去掉，日结不再丢。
  4. 代价与兜底：日志与日结只是文本，千条量级不过几百 KB；槽位仍有 96MB 上限兜底，
     真撑不住会在保存时明确报错，而不是静默丢历史。

FILES
  · src/rules/persistence.ts   去掉三处数量判断与任何裁剪；v1 迁移也不再截断
  · src/rules/core.ts          sampleFor 不再丢 60 天前的日结
  · tests/v194.test.ts         3 条
  · package.json / tasks/plan-v194.md / tasks/todo.md

EDGE IN
  · 301 条日志、61 天日结、单人 61 句对话：读档后一条不少
  · logs 不是数组：仍按坏档回落新开局（只放宽度量，不放宽类型）
  · 已经超限的旧存档：读档即恢复，不再显示未编成

EDGE OUT
  · 不限制运行中的历史继续增长（换来的就是完整保留）
  · 不为超长对话做分页渲染；对话界面仍会一次画出全部消息
  · 不改槽位的 96MB 上限与体积提示

ASSUME
  「保留全部数据」指日志、日结与对话这些历史记录；立绘等资产仍按现有的引用/瘦身规则处理。
