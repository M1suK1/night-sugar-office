# v30 方案：战斗札记改成连贯叙事 / 立绘放大 / 预设模型生效 / 上下文不再被截断

> 目标一句话：札记一次写完、至少 6000 字，不再像战报复盘；战斗舞台的立绘要看得清表情；预设里指定的模型必须真的生效；预设与战报不能被悄悄截断。

## 1. 范围

| # | 问题 | 主要落点 | 规模 |
|---|---|---|---|
| 1 | 札记按回合写、堆伤害数字与技能名 | `src/llm.ts` 的 `generateBattleNote`、`src/battleNote.ts` 的 `battleDigest` / 校验、`src/components/BattleNoteDialog.tsx` | 结构契约重写 + 上下文改写 + UI 去回合 |
| 2 | 战斗札记界面的立绘太小 | `src/combat.css` 的舞台列宽与 `.battle-note-portrait` | 尺寸 ×2 + 断点 |
| 3 | 预设里填的模型没生效 | `src/llm.ts` 的 `applyPresetApi` / 日志、`src/components/PresetDialog.tsx` | 生效链路 + 诊断 |
| 4 | 预设/战报内容被截断 | `src/presets.ts:269` 的 8000 字导入上限、`src/battleNote.ts:96` 的 160 条事件、日志与预算提示 | 上限、裁剪策略、显式提示 |

不做：不改战斗结算、胜负、奖励或角色状态；不引入新的模型供应商；不重做整个战斗剧场。

## 2. 现状与原因

### 2.1 札记生成（为什么像战报）

- `generateBattleNote`（`src/llm.ts:1632`）要求 **3–5 场、roundFrom/roundTo 连续**，并明确写「写清战况、谁救了谁、谁退缩了」；输出契约里每个 `line` 还带 `round`。
- `battleDigest`（`src/battleNote.ts:86`）逐条输出 `eventLine`：回合号、技能名、命中/伤害/治疗数值、资源变化；模型自然会把它们抄进正文。
- `BattleNoteDraftScene` 带 `roundFrom/roundTo`，`validateBattleNoteDraft` 要求场景覆盖回合且连续；UI 按「第 X–Y 回合」分场。
- 结果：文风像「战斗日志」，而不是「她回来之后把这一夜讲给你听」。

### 2.2 立绘尺寸

- 舞台三列：`.battle-note-stage.has-left/.has-right` 侧栏 `minmax(160px, 20vw)`；`.battle-note-portrait` `max-width: 330px`，dense 时 270px。
- 在 1440 宽下侧栏约 288px、立绘约 288px 高，五官与表情确实看不清。

### 2.3 模型没生效

- `applyPresetApi`（`src/llm.ts:597`）本身会读 `preset.api.model`，但生成日志里多处仍写 `config.model`（基础接口），面板参数与「实际请求」可能不是同一个值，容易误判。
- 预设编辑器里的「接口」区只在某些 provider 下显示模型字段；如果任务绑定的不是正在编辑的那份预设（战斗札记页显示的是副本/另一份），改了也不会进请求。
- 需要把「绑定预设 → 预设接口 → 最终请求模型」在日志和界面上串起来，才能判断是绑定错、字段没保存，还是代理把模型别名改写。

### 2.4 截断

- 导入 SillyTavern 预设时 `content.slice(0, 8000)`（`src/presets.ts:269`）：长写作指南会在第 8000 字处**静默切断**，日志里看到的就是半句话（「在开始写作之前，要判断自己处于」）。
- `battleDigest` 只取 `battle.events.slice(0, 160)`，超出部分**没有任何提示**；长战斗或多次尝试时会丢后半段。
- 预设的 `main`/长词条在 `composeTaskSystem` 里没有截断，但导入阶段已经丢了；再导出/再导入也救不回来，只能重新导入原始文件。

## 3. 设计

### 3.1 扎记：一次连续的战斗叙事

#### 3.1.1 新结构

`BattleNote` 增加 `format: 'continuous'`（旧札记没有该字段，按旧结构渲染）。**最终决策：不分段**，正文是一整篇连续的 `narration`，`scenes` 只保留一个容器给现有 UI 渲染，不再有场景标题与回合：

```ts
interface BattleNoteScene {
  title?: string;          // 可留空；只是分段小标题
  narration: string;       // 2–4 段，连续叙事
  lines: BattleNoteLine[]; // 去掉 round 字段
}
interface BattleNote {
  format?: 'continuous';
  title: string;
  hook: string;
  summary: string;
  scenes: BattleNoteScene[]; // 2–3 段：起势 / 转折 / 收束
  charCount: number; ...
}
```

- 不再有 `roundFrom` / `roundTo`，也不再有 `line.round`。
- 不按戏剧节拍切段：从头到尾一篇，用自然段推进；UI 只显示正文、对白与立绘，不显示“第几段/第几回合”。
- 旧札记兼容：没有 `format` 的按旧字段读取；新生成写 `format: 'continuous'`。

#### 3.1.2 上下文：只给「发生了什么」，不给数值

新增 `battleStoryDigest(battle)`：

- 保留：谁先出手、谁被压制、谁护住了谁、哪一下落空、哪一下改变了局势、谁倒下、最后谁站着、环境（辖区/污染档位/天气）；
- 去掉：回合号、伤害/治疗/护持数值、HP/心防数字、技能名、命中率、奖励数字（奖励只在单独一行给「报酬已结算」，不进正文）；
- 技能改成动作描述：例如「短促的突刺被外壳弹开」「一层薄薄的护持挡住了正面冲击」，而不是「星屑穿刺造成 64 点伤害」。
- 忠实性：只写真实发生过的命中/落空/倒下/护持；不发明新角色、新技能、新伤亡。

`battleCast` 仍然给 speakerId/表情表，模型只能从表里选说话人。

#### 3.1.3 提示词

- 明确：「这是一篇夜里写完的札记，不是战报。不要分回合，不要写伤害数字、回合数、技能名、HP/心防数值；用动作、停顿、表情与对白让读者自己看出局势。」
- 输出契约：`{format:'continuous',title,hook,summary,narration,lines[]}`；**全文 6000–10000 字**；台词 6–14 句，必须带 speakerId、speakerSide、六种表情之一、speech/thought。
- 保留「不改胜负、奖励、疤痕、角色状态」「不替玩家做决定」。
- 语气：避免「带着一丝不易察觉的愤怒」这类上帝视角解读；情绪放在动作与台词里（与用户写作指南一致）。

#### 3.1.4 校验

- 单篇正文 6000–10000 字（校验上限 12000）；
- 台词 speakerId 必须来自 cast，倒下后不能再说话；
- **禁用词/数字检查**：正文与台词中出现 `\d+\s*(点|伤害|回合|%|HP|心防)`、`第\s*\d+\s*回合`、技能目录里的技能名 → 记为硬错误，触发一次修复；修复仍犯就拒绝保存。
- 旧札记不做新校验；新札记写 `format: 'continuous'`。

#### 3.1.5 UI

- 舞台顶部不再显示「第 X–Y 回合」，也不显示场景号；正文连续滚动；
- 保留左右立绘与当前说话人高亮；
- 「来源」仍显示模型/模板；旧札记保留原回合标签（只读）。

### 3.2 立绘放大 2 倍

- 侧栏列宽：`minmax(160px, 20vw)` → `minmax(300px, 34vw)`；`.battle-note-portrait` `max-width` 330 → 660；dense 270 → 540。
- 舞台高度不变，立绘按 `object-fit: contain` 填满侧栏；中间正文列设最小宽度（`minmax(360px, 1fr)`），防止被挤没。
- 断点：
  - ≥1400：左右各 34vw，立绘 660；
  - 1024–1399：左右各 28vw，立绘 520；
  - ≤900：只保留说话人一侧（另一侧隐藏），立绘 420；
  - ≤640：立绘 300，正文在上、立绘在下（现有移动端顺序）。
- 头像/表情差分仍按 `expression` 切换，尺寸变大后 `portrait-vignette` 渐变收窄，避免吃掉脸。

### 3.3 预设模型真正生效

#### 3.3.1 生效链路

1. 日志与请求统一用 `cfg = applyPresetApi(preset, base)` 的 `cfg.model`，不再在日志里写 `config.model`；`requestParams` 用 `cfg`。
2. 预设接口区：只要 `preset.api.model` 有值，就覆盖默认模型；endpoint/key 缺失时分别回落到默认，不再要求「三项齐全」。
3. 绑定提示：战斗札记弹窗/生成日志显示「绑定预设：战斗札记 · <preset name> · 模型 <cfg.model>」；如果绑定的是只读内置预设，明确提示「当前用的是内置预设，改的是另一份」。
4. 启动时对已保存预设做一次校验：`api.model` 不是空字符串、没有首尾空格；导出/导入保留该字段。

#### 3.3.2 诊断与防呆

- 生成前把「请求模型」写进 `LlmRequestSnapshot.params.model` 与日志 `model`；两者不一致就是 bug。
- 连接测试与生成都用同一 `cfg`；测试连接成功后提示「实际模型：…」。
- 如果模型名在 Vertex 返回 404，错误里保留原模型名，提示检查预设/代理映射；如果代理把别名映射到别的模型，客户端无法感知，日志至少能证明发出去的是 `gemini-4-argon`。
- 新增单测：基础模型 `gemini-3.8-flash`、预设模型 `gemini-4-argon` → 请求体 model 必须是 argon，日志 model 也是 argon。

### 3.4 不再悄悄截断

#### 3.4.1 预设导入

- `content.slice(0, 8000)` → **不截断**（或上限 64k，仅防内存滥用）；
- 超长时在导入报告里写「词条 X 共 N 字，已完整保留」；如果确实要截，必须显式提示并标红，不能静默。
- 旧预设已经被截断的，只能重新导入原始文件；方案里提示用户重导一次。
- 保存到 localStorage 前检查容量，失败时回滚并报告，而不是存半份。

#### 3.4.2 战报

- `battleDigest` 改成分段压缩，不直接 `slice(0,160)`：
  - 保留前 80 条与后 40 条，中间按「局势变化」抽样，并在文本里写「中间 N 条已压缩」；
  - 或者按战斗阶段聚合：每 3 回合合并成一段摘要，再交给模型。
- 生成前统计 `battle.events.length` 与字符数；超过上下文预算时，优先压缩战报，不裁预设与角色卡；在日志里记「战报压缩：X → Y 条」。
- 请求快照记录每段的原始字符数与最终字符数；面板里能看出哪一段被裁。

#### 3.4.3 上下文预算

- `battle` 任务按 `maxContext` 计算：预设 + 角色表 + 战报 + 输出契约；若超预算，先压战报，再压世界书，最后才提示「请缩短预设/换更大上下文模型」。
- 生成前用 token 估算（已有 `promptTokens`）做一次上限检查，超限直接给可读错误，而不是让服务端截断。

## 4. 测试计划

- **结构**：新札记 `format`、无 round 字段、2–3 段、1200–2200 字；旧札记仍能渲染。
- **禁用内容**：正文含「64 点」「第 2 回合」「星屑穿刺」时校验拒绝并触发修复；修复后通过。
- **上下文**：`battleStoryDigest` 不含数字/技能名；事件 >200 时包含「已压缩」提示且保留首尾关键事件。
- **立绘**：1440/1024/390 三档下侧栏宽度与立绘宽度符合 2 倍规则，无横向溢出。
- **模型**：预设模型覆盖基础模型；日志与请求体一致；绑定只读预设时给出提示。
- **截断**：导入 12000 字预设完整保留；超 64k 才拒绝并说明；长战报不丢首尾。
- 预计状态测试 +10，浏览器 +2。

## 5. 验收

- [ ] 生成的札记读起来是一篇连贯的夜记，没有回合、伤害数字、技能名。
- [ ] 战斗舞台左右立绘约放大 2 倍，表情与眼神看得清，正文不被挤没。
- [ ] 战斗札记预设里填的模型出现在请求与日志里；改绑/改模型后下一次生成立即生效。
- [ ] 导入长写作指南不再出现半句话；战报过长时日志明确写「压缩了多少条」。
- [ ] 旧札记/旧预设仍能打开；新札记可保存、替换、删除。

## 6. 风险

| 风险 | 处理 |
|---|---|
| 模型仍写出数字/技能名 | 硬校验 + 修复一次；仍犯则拒绝保存并提示 |
| 去掉回合后叙事失去因果 | 上下文给「起势/转折/收束」三段式事件摘要，而不是只给结果 |
| 立绘放大挤掉正文 | 中间列最小宽度 + 900 以下只留一侧 |
| 预设模型是代理别名，客户端无法验证 | 日志记录发出的 model；连接测试显示实际模型；错误保留原名 |
| 旧预设已被截断 | 明确提示重新导入原始文件，不做不可靠的“复原” |

## 7. 实施顺序

1. 立绘尺寸（纯 CSS，最快看到效果）。
2. 预设模型生效 + 日志统一（先让「用的哪个模型」可验证）。
3. 预设导入上限 + 战报压缩（先保证输入完整）。
4. 札记结构契约、提示词、校验与 UI（改动最大，最后做）。
5. 回归、构建、浏览器验收与文档。
