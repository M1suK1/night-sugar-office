# v83 用卡库小卡替代内置默认角色

## 一、要解决的事

1. **开局名册**：现在一开新游戏就是 `content/seed-pack.ts` 的 6 位内置少女（月见桃、砂糖、零青、雾眠、栀子、鹿铃），卡库只用来「额外挑几个」。改成：默认名册直接来自 `data/cards/` 里的契约卡。
2. **所有缺省取人的场合**都统一走卡库，卡库不可用才退回内置：
   - 市场候选池补货
   - 候选池低水位补齐
   - 空白档开局
   - 编成池的三方首领与随从
   - 叙事者起草失败时的兜底角色
3. **不可用要说得明白**：纯静态部署没有 `/api` 通道，必须显式提示「本次用内置名册」，不能像现在这样静默。

## 二、现状（查证过的落点）

| 事实 | 位置 |
| --- | --- |
| 内置 6 人 + 委托 + 房间都在一个静态包里 | `src/content/seed-pack.ts`、`src/rules/state.ts` 的 `createInitialState()` |
| 三方首领/随从是静态表 | `src/content/factionLeaders.ts`、`src/content/factionGirls.ts` |
| 卡库通道已经存在 | `GET /api/cards`（扫描，只回 hash/名称/大小）、`GET /api/cards?name=`（单张读），见 `scripts/local-files.mjs`、`scripts/cards-api.mjs` |
| 市场补货已经会用卡 | `applyRefillMarket`（`src/rules/cardOps.ts`）+ App 传 cards |
| 开局只把卡库当「加菜」 | `startNewGame`（`src/App.tsx:961`）先 `reset` 成内置名册，卡库面板只是挑人入口；`loadCardBox()` 失败就直接内置开局 |
| 候选池不足时是「合成」而不是卡库 | `src/rules/candidate.ts` |
| 卡库体积 | 本地 33 张 / 约 247MB；其中 17 张 ≤3.5MB 已入库，13 张 3.5–21MB 只在本地 |

结论：缺的是**一个统一的「角色来源」层**，而不是再写一套导入逻辑。

## 三、方案

### 3.1 新增 `src/cardLibrary.ts`（角色来源层）

```
scanLibrary(): Promise<LibraryScan>            // 缓存 {hash, name, size}，TTL 30s，失败返回 {ok:false, reason}
readLibraryCard(entry): Promise<Girl | null>   // 单张读取 + parseGirlCard + 立绘入库
pickLibraryEntries({count, exclude, purpose})   // 小卡优先 + 稳定洗牌（种子=day+用途），同一局可复现
LIBRARY_BYTES_BUDGET                           // 一次读入上限，默认 24MB，可在数值设置里改
```

- **只拿元数据**：扫描阶段绝不读 base64；列表里带 `size`，用来做「小卡优先」与预算裁剪。
- **读完即瘦**：单张读进来后立刻走现成的 `extractStatePortraits` 把立绘搬进资产库，state 只留引用（v92 已有链路），避免又一次 OOM（v42 的教训）。
- **稳定**：同一局同一用途拿到的永远是同一批人，不会因为重开面板就换脸。

### 3.2 开局改成「卡库铺池，玩家挑」

1. `createInitialState` 增加参数 `{ roster: 'seed' | 'empty' }`：`empty` 只给房间/委托/经济骨架，名册与候选取空。
2. `startNewGame`：
   - `scanLibrary()` 成功 → `reset({roster:'empty'})` + 取 `OPENING_CARDS`（30）张进候选池 → 打开卡库面板挑人（沿用现有编成流程）。
   - 失败 → 现状保持不变（内置 6 人），并在卡库面板顶部写清原因与「如何启用本地卡库」。
3. 卡库卡进名册后 `startersPicked = true`（v129 已经这么做了，继续沿用）。

### 3.3 缺省补位统一入口

```
fillFromLibrary(state, need: {candidates?, leaders?, roster?}): ActionResult
```

接进这些地方，优先级一律「卡库 → 内置 → 合成」：

| 场景 | 现在 | 改后 |
| --- | --- | --- |
| 市场补货 | 卡库（无预算、无排序） | 卡库小卡优先 + 预算 + 统一去重 |
| 候选池低水位 | `candidate.ts` 合成 | 先卡库；卡库耗尽才合成，并在日志标「临时合成的角色」 |
| 空白档开局 | 空名册 | 卡库可用时铺满候选池 |
| 编成池首领/随从 | 静态表 | 见「待定 1」 |
| 起草失败兜底 | 内置模板 | 卡库随机一张（有卡时） |

### 3.4 数据与不变式

- 卡库只决定「从哪来人」，不改任何规则数值；卡里的等级/技能/语料原样进档（与现在导入卡完全一致）。
- 存档只存角色本体 + 资产引用，不存卡库路径；换机器、删卡都不影响已有存档。
- 同一局去重继续用 `usedCardIds`。
- 卡库读失败（单张坏了）只跳过并计数，不阻塞开局。

### 3.5 UI

- 卡库面板顶部：「本地卡库 · N 张（可用 x 张）」，本次将使用的名单，一个「换一批」。
- 没连上卡库：一条明确提示 + 说明（`npm run dev` / `start.cmd` 才启用本地区道）。
- 编成界面里来自卡库的人打「卡库」标签，内置的标「内置」。

### 3.6 测试

- 单测（`tests/v135+`）：扫描解析与失败回退、稳定洗牌与去重、预算裁剪、`fillFromLibrary` 不超上限、单张坏卡只跳过。
- 规则测：`reset({roster:'empty'})` 保留房间/委托/经济；导入卡后 `startersPicked` 为真。
- 端到端（本地 dev）：扫描 → 开局 → 名册全部来自卡库；把 `/api` 关掉时回退内置并提示。
- 全量回归：现在 94 文件 649 项必须保持绿。

### 3.7 分批

1. **批 1 · 来源层**：`cardLibrary.ts`（扫描/读取/预算/稳定洗牌）+ 卡库面板显示「本地 N 张」+ 单测。
2. **批 2 · 开局**：`reset({roster:'empty'})`、`startNewGame` 走卡库铺池、失败回退与提示、测试。
3. **批 3 · 缺省补位**：市场/候选/空白档统一走 `fillFromLibrary`，首领与随从按「待定 1」接入，起草失败兜底。

## 四、风险与取舍

- **只有本地跑才有卡库**：网页部署版永远走内置回退。方案里把它做成「明示降级」，而不是假装有。
- **大卡会卡顿**：13 张 10–21MB 的卡必须懒读 + 预算，否则会重演加载爆炸。
- **开局强度会随卡漂移**：卡是导出时的快照，等级可能很高。要么原样继承（简单、但开局可能过强），要么开局压级（见待定 3）。
- **卡与内置的数值口径不同**：技能、特性、语料都由卡带来，内置角色反而成了「另一套标准」。批 1 会把两套都跑一遍测试，避免出现只有内置能过校验的情况。

## 五、待你决定

1. **三方首领/随从怎么取卡**：A 自动挑（按等级/技能筛 + 稳定随机，推荐）／ B 在设置里为三方各指定一张卡 ／ C 用 `data/cards/leaders.json` 映射文件。
2. **开局铺多少人**：沿用现在 6 人，还是按 `OPENING_CARDS=30` 铺满候选池让玩家自己挑。
3. **卡库卡的开局等级**：原样沿用卡里的等级，还是统一压到 1–3 级（避免开局过强）。
